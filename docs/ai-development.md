# OpenCode 开发过程记录（ai-development.md）

> 题目 §7.3 要求提供三个阶段的开发过程证据。本文按阶段记录**实际发生**的
> 过程：做了什么、OpenCode 承担了什么、哪些决策由人做出、遇到什么问题、
> 如何验证 AI 产出的代码确实满足需求。

---

## 1. 总览：OpenCode 承担的任务

| 阶段 | OpenCode 承担的工作 | 人承担的工作 |
| --- | --- | --- |
| 一、需求理解与技术设计 | 解析题目、拆解 F1–F6 与接口契约、枚举 ASR 候选方案及取舍、产出开发计划与阶段任务表 | 拍板关键决策（引擎、Python 版本、是否做实时、模型规模、样本来源）；审阅并确认计划 |
| 二、功能开发与集成 | 生成后端分层代码、音频解码层、引擎抽象与真实引擎封装、前端页面与录音/实时逻辑、脚本与配置 | 确认技术方向；对不确定处要求先给方案再动手（"先出计划再开发"） |
| 三、测试与问题修复 | 生成 pytest 用例（Mock + 真实模型两层）、定位并修复运行期缺陷、生成文档与说明书 | 提供测试音频与参考文本；确认已知问题是否可接受 |

**使用的工具形态**：以 OpenCode 的代码模式（Code Mode）为主，辅以 shell 命令执行
与浏览器工具做端到端验证；模型为编码模型，未额外挂载 MCP Server 或自定义 Skill
（题目不强制要求）。

## 2. 阶段一：需求理解与技术设计

### 2.1 过程

1. **让 OpenCode 先读题、再总结**。要求它把题目解析为"功能需求 / 接口契约 /
   约束 / 测试要求 / 交付物"五块，而不是直接开始写代码。
2. **环境核对**。让它核查本机环境，结果暴露两个问题：
   - 工作目录是空仓库，需要从零搭建；
   - 本机只有 Python 3.11.9，而题目要求 3.12。
3. **产出开发计划**（`docs/development-plan.md`），包含 8 个阶段（P0–P8）、
   每个阶段的任务表、交付物、验收标准、两天排期、风险与应对。
4. **人就计划中的关键决策拍板**，确认后才进入开发。

### 2.2 由人做出的重要技术决策

| 决策 | 选项 | 人的选择与理由 |
| --- | --- | --- |
| ASR 引擎 | faster-whisper / sherpa-onnx / vosk / 双引擎 | 选 **faster-whisper**：一个模型覆盖中英文、CPU int8 可用、pip 免编译 |
| Python 版本 | 沿用 3.11 / 安装 3.12 | 选**安装 3.12 并用项目内 venv**：与题目环境严格对齐，避免复现风险 |
| 实时识别 | 做 / 不做 | 选**做**：加分项，且已有清晰的"分片 + 滑窗重识别"可行路径 |
| 测试音频 | TTS 生成 / 下载公开音频 / 自行录音 | 选**自行录音**：内容可控、版权清晰、不含他人隐私 |
| 默认模型规模 | tiny / base / small | 初选 **small** → 依 TTS 实测改为 **base** → 依真实录音实测**改回 small**（base 在真实录音上中文相似度仅 0.611，small 为 0.986） |

> 这些决策没有被交给 AI 自行决定——它们直接影响交付质量与合规性，
> 必须由人对结果负责。

### 2.3 为什么"先出计划再开发"

题目只给 2 天，最大的风险不是写不出代码，而是**方向错了返工**。因此流程被约束为：

```text
读题 → 计划（含决策点与验收标准）→ 人确认 → 开发 → 每阶段跑测试保持绿色
```

后续实践证明这一步是划算的：`docs/development-plan.md` 里的"接口契约冻结"
使得前后端可以并行推进，而"风险表"中列出的两条风险（WebM/Opus 解码、
模型下载受限）后来**都真实发生了**，且都有预案。

## 3. 阶段二：功能开发与集成

### 3.1 开发顺序（自底向上，先契约后实现）

```text
P0 脚手架与依赖
P1 后端骨架 + 三接口（先接 Mock 引擎，让契约先跑通）
P2 音频解码层（最高风险，优先做）
P3 ASR 引擎抽象 + Mock 引擎 + 注册表
P4 真实 faster-whisper 集成
P5 前端（录音 / 上传 / 结果 / 错误）
P6 实时识别（WebSocket + AudioWorklet）
P7 测试补全
P8 样本、文档、交付检查
```

关键做法：**P1 就用 Mock 引擎把三个接口打通**，这样后端契约在前端动工前已经
可验证；P3 的引擎抽象让 P4 只是"换一个实现"。

### 3.2 OpenCode 生成的代码如何被约束

在提示中明确要求，而不是让模型自由发挥：

* 依赖方向：`api → services → core/asr`，`core` 不得依赖 FastAPI；
* 所有失败路径必须走统一 `AppError` 体系，由 `main.py` 的处理器序列化；
* 语言参数必须支持别名归一化（`zh-CN`、`English` 等）；
* 前端不得引入任何构建步骤或第三方库（题目禁止 Node.js 成为运行必需）；
* 每个阶段结束时必须跑 `python -m pytest -q`。

### 3.3 集成中暴露并修复的问题

| # | 问题 | 定位方式 | 修复 |
| --- | --- | --- | --- |
| 1 | `pip install` 默认源读超时 | 报错栈显示 `files.pythonhosted.org` ReadTimeout | 先用镜像源解决当下阻塞；最终把 `--index-url` 写入 `requirements.txt` 首行，使"`python -m pip install -r requirements.txt`"这条**题目规定的启动命令**在受限网络下开箱即用 |
| 2 | PyAV 19 中 `av.open(..., metadata_errors=...)` 参数不存在，导致 **WebM/Opus 解码全部失败** | 用最小复现脚本单步执行解码流程，拿到 `TypeError: open() got an unexpected keyword argument` | 移除该参数；并为此前的"静默失败"补上分步日志，避免再次难定位 |
| 3 | HuggingFace 官方域名连接被重置，模型下载失败 | 下载脚本日志 `ConnectError: WinError 10054` | 改用国内镜像；最终**移除官方源路径**，HF 端点固定为镜像 |
| 4 | 镜像把请求重定向到 `cas-bridge.xethub.hf.co`，实测仅 **25 KB/s**（483 MB 需要约 5 小时） | 用 `curl -w speed_download` 量化测速，并对比多个下载源 | 改用 **ModelScope**（实测 6.4 MB/s，约 1 分钟完成），并作为**唯一下载来源** |
| 5 | requirements 文件里的 `--index-url` 会覆盖命令行 `-i`，使用者可能无法切回官方源 | 用临时 requirements 文件做 4 组对照实验（CLI `-i` / `PIP_INDEX_URL` / `PIP_CONFIG_FILE` / 无配置） | 确认覆盖关系后按"唯一来源"定稿：在 `requirements.txt` 顶部与 README §3.4 明确写出该行为与取舍理由 |
| 6 | `encode_wav` 只写单声道，立体声测试输入被当成双倍时长的单声道 | pytest 断言失败（4.0s ≠ 2.0s） | 给 `encode_wav` 增加 `channels` 参数 |
| 7 | 语言别名缺 `en_GB` | pytest 参数化用例失败 | 补齐别名表 |
| 8 | 中文输出为繁体（「歡迎」） | 浏览器实测真实模型结果 | 增加 `ASR_INITIAL_PROMPT_ZH` 提示词机制 |
| 9 | 加上简体提示词后，**短音频出现幻觉**（6 秒音频识别成"这次的节目是《欢迎使用语音识别系统》。"） | 对比"有/无提示词"在同一音频上的输出，并对比不同音频长度 | **用数据做决策**：默认关闭提示词（保留为可选项），并把实时识别的最小缓冲从 0.4 s 提到 1.0 s |
| 10 | 手工测试脚本用 `subarray(...).buffer` 发送音频，服务端时长翻 5 倍（5 s → 25 s） | 对服务端返回的 `duration_seconds` 做断言时发现异常 | 测试改用 `slice()`；在前端 `pushPcm` 处补注释说明必须新建等长数组 |

问题 2 值得强调：**如果只依赖"看起来能跑"，WebM/Opus 这条最关键的解码路径会
在演示时才暴露问题**。因此专门写了单步解码脚本来验证每一种输入格式。

问题 4 与 9 体现了同一条原则：**不要凭直觉选方案，要用可测量的数据选方案**。
前者是下载速度，后者是识别准确率——两者都用最小实验对比后做了取舍。

**同一原则也用在了模型规模的最终选定上，而且反复用了一次**：

1. 计划评审时默认档位定为 `small`；
2. 用 `scripts/benchmark_models.py` 在 **TTS 合成样本**上实测三档后，发现 `base`
   的中文相似度 0.974、速度约为 `small` 的 3 倍，且实时识别从"11 秒音频超过 60 秒
   未完成"变成"6.8 秒完成"——于是把默认档位改为 `base`；
3. 后来把样本换成**作者本人的真实录音**复测，`base` 的中文相似度骤降至 **0.611**
   （且输出繁体），而 `small` 仍为 **0.986**——于是把默认档位**改回 `small`**。
   该录音仅本地测试用、不随仓库分发（个人数据），实验数据保留在测试报告中。

结论与两轮数据都写进了 `docs/design.md` §4.3 与 `docs/test-report.md` §3.5–§3.7；
原始决策与每次变更的原因保留在 `docs/development-plan.md`，而不是悄悄改掉。

**这里最重要的不是结论，而是结论被推翻的过程**：如果只用合成语音评估，就会带着
"base 够用"的错误判断交付。样本的代表性直接决定了选型结论是否可信。

## 4. 阶段三：测试与问题修复

### 4.1 测试策略（对应题目 §6.1 的硬性要求）

```text
python -m pytest -q                # 100 用例，全 Mock，不联网、不下模型、不用麦克风
python -m pytest -q -m real_model  # 真实 faster-whisper 的中英文识别 + 相似度断言
```

两层测试通过 `ASREngine` 抽象分离：

* `pytest.ini` 中 `addopts = -m "not real_model"`，保证常规命令**永不**触发模型下载；
* `conftest.py` 在导入应用前强制 `ASR_ENGINE=mock`，从根上杜绝误用真实模型；
* 真实模型用例会先尝试加载模型，不可用时 **skip 而不是 fail**，保证在未初始化
  模型的环境中也能得到有意义的测试结果。

### 4.2 由测试驱动发现的问题

* 立体声重采样错误（见上表 #4）——由 `test_decode_downmixes_stereo` 捕获；
* 语言别名缺失（#5）——由参数化用例 `test_english_aliases[en_GB]` 捕获；
* 静音输入的期望行为——最初 Mock 引擎对静音也返回文本，与真实模型行为不符，
  于是让 Mock 对全静音返回空文本，并在 `test_silent_audio_returns_empty_text_without_error`
  中断言，使 Mock 与真实模型的契约一致。

### 4.3 一次完整的"错误定位 → 修复 → 回归"链条（示例 #2）

```text
现象：编码 WebM/Opus 后再解码 → DecodeFailedError
① 怀疑是编码侧问题 → 打印编码后字节数与魔数 → 编码正常（webm，11.5 KB）
② 怀疑是解码侧问题 → 把 decode_audio 内部逻辑拆成脚本逐步执行
③ 拿到真实异常：av.open() 不支持 metadata_errors 参数（PyAV 19 API 变化）
④ 修复：去掉该参数
⑤ 回归：重跑单步脚本 → 16000 采样 / 1.0 s；重跑 pytest → 100 用例全绿
⑥ 加固：为解码失败补充分步 debug 日志，避免同类问题再次"静默"
```

## 5. 如何确认 AI 生成的代码满足业务需求

不依赖"看起来对"，而是四道关卡：

| 关卡 | 手段 |
| --- | --- |
| 契约层 | 逐条对照题目 §4 的接口/字段/错误码，用测试断言锁死（含 `/health` 只返回 `status`） |
| 行为层 | 100 个 Mock 用例覆盖 F5 的 8 类异常场景、"无有效语音返回空文本而非报错"等边界 |
| 集成层 | 用真实 WebM/Opus 字节流验证浏览器录音格式，用 TestClient 走完整 HTTP 与 WebSocket 流程 |
| 真实模型层 | `-m real_model` 用真实权重识别中英文样本，与人工参考文本做相似度断言（不设满分断言，避免过拟合到某次输出） |

此外，前端契约也有测试保护（`test_frontend_contract_references_required_endpoints`），
确保页面确实调用了 `/api/transcribe` 并按题目提供了 zh/en 选择与复制能力。

## 6. 如果继续优化，会优先改进什么

按优先级排序：

1. **实时识别体验**：引入 sherpa-onnx 的原生流式 Zipformer 作为实时通道的专用
   引擎，替换当前的"全量重识别"，把延迟从秒级降到百毫秒级，并消除长句中间结果的
   重排现象。
2. **中文输出规范化**：目前"繁体/简体"与"提示词诱发幻觉"之间存在取舍，默认关闭提示词。
   下一步计划引入**简繁转换后处理**（确定性映射，不经过模型），既统一为简体又不引入幻觉；
   同时为中文补充领域热词表。
3. **模型分发**：提供权重校验（sha256）与一键离线包，彻底消除评委首次运行时的
   网络依赖。
4. **并发与资源**：把推理改为有界队列 + 单 worker 进程池，支持多人同时使用而不
   互相阻塞；加入推理超时与取消。
5. **可观测性**：结构化 JSON 日志 + 每次识别的请求 ID，便于问题回溯。
6. **测试**：补充真实模型测试的一致性回归（同一音频多次识别的方差），
   以及前端录音逻辑的浏览器自动化测试（Playwright）。
